# V0.3 前置角色与部件流程：已确认方案

确认日期：2026-09-12。

状态：产品方案已确认，待实现与验收。本次是文档变更，不代表 AI 接口、抠图检查台、表情换图或云端部署已经完成。当前可运行编辑器仍为 V0.2 Beta，其能力和测试边界见 README 与 v0.2-qa.md。

## 1. 不可变更的生产决策：AI 部件生图只走纯色色键路线

所有 AI 生成的角色零件，包括图生图、补绘、替换件及后续新增服务商，统一要求高对比度纯色背景。取消“模型原生透明优先、失败再抠图”的双路径。即使某个模型支持透明，也不在部件生图中启用。

固定流程：角色版本 + 拆件清单 → 高对比度纯色部件图 → 背景检查 → 抠图及边缘去色 → 语义分组与独立裁切 → RGBA PNG 检查 → 部件库 → 拼装与动画。

统一的是流程，不是永远使用同一种颜色。按角色配色选择背景色，允许人工覆盖；同一批次固定一种颜色，并记录请求色和实测背景色。更换模型不得自行更换处理路线。背景应与主体颜色明显区分，而非只比主体更亮。

当前银紫色头发魔法师可优先测试绿色；绿色角色可以选择品红或其他不冲突颜色。无法确定安全背景色时须提示确认，不能为强行抠图而抹掉主体同色区域。

适用范围仅为 AI 部件生成。角色概念设计、原画上传不强制使用色键；外部已做好的透明 PNG/部件 ZIP 仍可经检查直接导入，不要添加背景后再次抠图。

稳定性目标是统一可验证的输出规范与失败处理，不是宣称任何 AI 输出都能百分之百无损抠图。发光、半透明纱、复杂透射不纳入首版通用抠图保证。

## 2. 解耦入口和五步流程

入口：描述生成角色、上传已有角色、导入现成部件、继续已有工程。没有配置 API 时，已有素材的拼装、绑骨、动画与导出必须仍然可用。

五步：准备角色 → 选择用途 → 准备并检查部件 → 拼装与绑骨 → 制作动作并导出。

角色生成支持需求对话或结构化选项。编辑需求不自动触发付费生成，点击生成才提交请求。用户明确采用某张图片后建立不可变角色版本；后续修改另存版本。上传原画不自动重画或覆盖。三视图是可选参考；多视图设计稿需要选择本次使用的视图。

## 3. 用途决定拆件，不按动作重复生成整套角色

预设：头像与表情、角色待机、基础游戏动作。允许合并用途，并去重拆件清单。

拟定七个基础动作：待机、行走、跑步、跳跃、攻击、受击、倒地。它们是产品规划，不是已实现能力，也不是已核实的开源项目。用户提到的开源项目尚未识别，确认名称、许可和骨架兼容前不作为依赖。

同一适用视图尽量复用一套素材与骨架；必要的手型或透视变化增加替换件。不同视角需要单独准备和确认，不承诺正面贴图直接变成自然的侧面跑步。

## 4. 部件生成与检查台

先确认稳定编号与语义名称的部件清单，再按头部、手臂、下半身等分组生成。保持多部件同图；不要求每个部件单独调用模型，也不要求 AI 生成最终运行时 Atlas。

可见区域优先研究保留原始像素，缺失和遮挡区域再补绘。输出是候选素材，须检查数量、语义、风格、比例、遮挡补绘、边缘和背景。连通区域数量不是部件数量；同一部件允许包含多个分离像素区域。

检查台状态：可用、待确认、缺少、重复、需要修复。支持手工归组、命名、分开粘连件、调整蒙版和仅重做失败部件。确认件不随重试其他部件被覆盖。重生成替换件保留历史并对齐确认后替换。

## 5. 与 V0.2 编辑器的数据衔接

保留 Asset、Part、Bone、Clip 分层；AI 服务、外部 PNG 和外部 ZIP 最终通过统一部件包导入。

建议前置数据独立保存角色版本、生成任务、部件候选和检查结果；迁移编辑器工程格式时明确升级版本，不让旧解析器静默丢失新字段。不得把 API Key 放进工程包。

必须分开记录 source_bbox（素材板裁切位置）、setup_transform（角色初始摆放）和 pivot/关节。source_bbox 不能用于宣称自动还原角色。保留原图坐标的分割件可复位；重新生成并重新排布的素材只能给出对齐建议，供用户确认。

眨眼及嘴型需要新增插槽/Attachment 替换轨道、预览、保存和导出支持。当前骨骼变换轨道不能冒充已经支持表情换图。动作模板通过语义骨骼映射适配，并允许纠正，不仅依赖文件名猜测。

## 6. API、隐私及任务边界

规划 OpenAI 图片接口适配器、Gemini 原生适配器和经验证的第三方兼容适配器。请求/响应结构分别处理。聊天接口连通不等于图片编辑可用；文生图、带参考图编辑分别验证。不支持的功能明确报错，不静默退化为无参考图生成。

部件任务固定 chroma-only；服务商支持透明与否不影响路线。仅发送该服务实际支持的参数：有不透明选项时使用，不得盲目向所有服务发送同名背景参数。没有原生背景参数时由提示词要求纯色并在返回后验收。未通过背景验收的结果不得绕过抠图检查直接入库。

配置字段：服务类型、可信 HTTPS 接口地址、模型名和 API Key。首版内部工具由管理员配置服务端密钥，前端通过登录后的服务端代理发请求。密钥不得写入前端包、GitHub、项目文件、截图或完整日志；自定义地址受管理员白名单限制。对话整理可先用固定模板，需要语言模型时另行配置，不强制增加调用。

付费测试须明确确认。使用任务编号、请求去重、可恢复状态和限额；页面刷新/切后台不自动重复生成。对超时但上游结果未知的请求不盲目自动重试。取消不承诺上游停止计费。费用估计不准确时显示未知，不显示为零。

明确告知用户 AI 阶段会把选定原画和提示词发给对应服务。保存输入和输出的范围、保留期限、删除入口需可见；本地导入和编辑不得因新增 API 而被迫上传。

## 7. 部署方向

规划 Cloudflare 静态网页 + 服务端代理；生成任务、密钥和临时素材分层处理。编辑工程仍支持本地保存，首版不强制开发云端协作。

Cloudflare 账号权限、资源额度、域名绑定和运行限制须部署时验证。此方案及本文提交不是网站已上线的证据；不修改现有域名记录，不自动启用付费资源。

## 8. 分期交付

第一阶段：角色描述生成/上传 → 头像清单 → 两类图片适配 → 统一色键及检查台 → 导入拼装 → 眨眼换图轨道 → 资源导出 → 指定 Laya 版本实测。

第二阶段：全身待机方案、骨架模板、动作适配，逐项增加和验收七个基础动作。

第三阶段：补绘与自动对齐质量、局部修复；按需求增加 IK、网格和权重。不能以功能按钮代替实现和验证。

## 9. 验收标准

- 所有 AI 部件任务均走纯色色键路线；没有原生透明开关、优先级或静默回退分支。
- 更换服务商仍输出同一部件包结构；外部透明部件可直接导入。
- 背景检查、蒙版、去色、裁切参数和失败原因可追溯；同一输入与同一处理版本可重复复现。
- 输出每个零件为真实 RGBA PNG；白底、深色底、检查网格上复核细节，不烘焙检查背景。
- 缺件、粘连、误分割或色彩冲突明确提示，未经确认不冒充合格。
- 原图、已确认部件及历史版本不被重试覆盖；替换件须确认对齐与绑定。
- 不配置 API 仍可完成手工编辑；手机刷新可恢复任务状态，不重复计费提交。
- 表情和动作保存重开不丢失；导出与预览一致，并在确定版本的 Laya/Cocos 工程分别验收。
